# 中国业务场景指南

按实际用户、渠道和交付方式选择条目，不给所有项目套同一组业务假设。参考来源见 [pm-source-map.md](pm-source-map.md)。

## 场景路由

| 场景 | 先明确 | 写入需求与验收 |
| --- | --- | --- |
| ToB / SaaS / 企业内部系统 | 使用者、采购者、业务决策者、IT 管理者是否不同；谁承担实施成本 | 组织/租户/角色/数据权限，审批、导入导出、审计、迁移、培训和验收责任 |
| ToC / 内容 / 交易 | 首次核心价值是什么；获客渠道和回访动机 | 新老用户分层、转化分母、留存周期、取消退款及客服处理（适用时） |
| 微信小程序 / 企微连接场景 | 入口是搜索、扫码、分享还是已有客户触点；宿主身份能力有哪些限制 | 授权拒绝后的路径、登录失效、重复点击、返回与恢复、弱网、通知触达边界 |
| 电商 / 本地生活 | 谁提供服务、谁收款、平台承担什么责任 | 订单/支付/履约/售后状态，对账口径、优惠成本、退款和异常恢复 |
| AI 产品 / AI 功能 | 输出是否可验证；哪些结果须由人接受 | 代表性评测集、质量阈值、延迟与单次有效结果成本、失败/未知状态、转人工 |

## 需求入口与组织协作

常见入口有用户访谈、客服工单、销售反馈、业务负责人要求、运营数据和平台规则变化。入口是来源，不是优先级证明。同一问题合并后保留来源及群体，不能把同一投诉的多次转述计成多个独立用户。

ToB 按角色区分目标：

- 使用者：能否完成实际工作，操作成本是否下降。
- 业务决策者/采购方：预算、经营收益、采购及合同边界。
- IT/管理员：组织权限、部署集成、数据迁移和运维约束。
- 销售/实施/客户成功：报价内容、交付范围、配置与定制边界、培训及支持成本。

需求评审明确目标、方案与范围；技术评审由研发确认实现和估算；测试验收核对规则与可观察结果；上线评审确认灰度、运营与回退。小团队可合并会议，但保留决策责任和依据。文档生成不等于这些角色已经批准。

## ToB 标准化与定制

客户要求标记为标准能力 / 可配置能力 / 项目定制 / 暂缓。评估同类客户可复用性、配置复杂度、实施工作、升级兼容及维护成本。

商业范围说清：谁买、为何买、买哪些能力及服务、如何收费、如何交付验收。需要时在 `prd/00`、`12`、`15` 写报价边界、接口数量、迁移责任、发票/回款节点；这些须来自实际业务，不能由模板自动补成合同承诺。

## 渠道与增长

微信、企微、公众号、抖音、小红书、应用商店等只是候选渠道。根据人群和资源选择，记录获客成本、激活、留存、有效成交及售后代价。展示量和粉丝数不能直接代表产品价值。

渠道规则、接口能力、收费和服务类目会变化；涉及具体能力时核对当期官方文档，附访问日期。不要凭历史印象声称“可自动发消息”“必然通过审核”或保证到账时间。

## 界面与业务口径

- 中文长名称、空值、超长表格、批量操作结果、权限不足提示要有处理方式。
- 金额写币种与税口径；时间写时区、自然日/工作日及节假日规则；手机号、地址按真实范围设计。
- 身份与联系方式只在业务需要时收集，写明用途、拒绝后路径、保存和删除需求。真实访谈身份或密钥不放入公开 PRD。
- 涉及支付、内容、未成年人、敏感信息或行业准入时，记录对应产品问题、官方依据与责任人；只核查相关要求，不自动声称“已合规”。

## 工具落地

在飞书、TAPD、禅道、PingCode 或 Jira 中均可沿用需求、规则和验收编号。默认交付 Markdown 表格，供团队映射实际字段；只有实际执行并得到可核查结果后，才称为已同步工具。
